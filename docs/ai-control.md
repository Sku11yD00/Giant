# Driving the editor with AI

Everything the editor can do is a command (AGENTS.md rule 7). The same
commands are available to people (menus and panels), to C# scripts, to the
built-in assistant (the chat with Claude, below), and to outside AI tools
through MCP.

## Connect Claude Code

The editor is an MCP server on stdin/stdout when started with `--mcp`.
Claude Code starts it for you. On Windows, from the folder that holds
`giant_editor.exe`:

```
claude mcp add giant -- giant_editor.exe --mcp
```

Or put this in a `.mcp.json` next to your project (use the full path to the
exe):

```json
{
  "mcpServers": {
    "giant": { "command": "C:/Giant/giant_editor.exe", "args": ["--mcp"] }
  }
}
```

The editor window opens when Claude Code connects and closes when it
disconnects. Ask things like "make the background a sunset orange" or "what
GPU is the editor using?" or "build a small village with a church and light it
like late afternoon"; Claude calls the tools, looks at the result with
`capture_screenshot`, and can undo what it did.

## The chat with Claude, inside the editor

The editor has its own assistant: you write what you want in plain words
("plant a row of trees along the road", "why is this person standing
still?") and Claude does it, with the same commands your buttons run. What
it changes in the scene is on the undo history like your own work.

It needs two things:

- **Your Claude key.** Make one in the Claude Console
  (platform.claude.com), then either set the `ANTHROPIC_API_KEY`
  environment variable before starting the editor, or put the key alone on
  the first line of a text file: `%APPDATA%\Giant\claude_key.txt` on
  Windows (`~/.config/Giant/claude_key.txt` on Linux). The file is read
  with every message you send, so the editor need not be restarted for a
  new or corrected key. The key is only ever read from those two places:
  it is not in the project, not in saved scenes, not in the log, and no
  game made with the engine contains the chat at all. It is sent only to
  Claude's service (unless you set `ANTHROPIC_BASE_URL`, which points the
  chat at another address). Using the chat is paid for by that key, by the
  amount of text sent and received (`get_chat` counts the tokens, roughly:
  see your usage in the Claude Console for the bill).
- **The .NET 10 runtime**, as C# scripts do.

The **Chat panel** (View menu; on the right in the default layout, so use
View, Reset layout if you do not see it docked) is where you use it: write
in the box at the bottom, up to about 4,000 characters, and press Enter
(Ctrl+Enter or Shift+Enter starts a new line). Claude's answers appear above, with a dim line for each command it
runs; one that did not work is shown in yellow with why. **Stop** halts
its work, **Clear** starts a new conversation, and **Details** shows what
each command was given and gave back. If a message cannot be sent (no key
yet, say), the reason is shown above the box.

**Ask me before changes** (ticked when the editor starts) makes Claude
wait for your yes before each command that changes something. A small
window in the middle of the editor shows the command, what it is for and
what it was given (the first 16,000 bytes when it is longer, with how much
is left out: do not allow what you cannot read), with three buttons: **Don't allow** (the
command is not run, and Claude is told it was your decision), **Allow**,
and **Allow everything for this message** (no more questions until Claude
has finished with what you last wrote; your next message asks again).
Commands that only look at the scene never ask (taking a screenshot counts
as looking, though it writes a picture into the `screenshots` folder).
Loading a script file by command asks you in a window of its own
(`docs/scripting.md`). Untick the box to let
Claude work without asking; it is ticked again the next time the editor
starts. The answer is yours alone: only the window's buttons give it, and
no command does, so neither Claude nor a tool nor a script can answer for
you or untick the box. Stop and Clear withdraw a question that is open.

The panel is these commands, which the AI over MCP can use too:

| Command | What it does |
| --- | --- |
| `chat_send` | Sends `text` to Claude. Returns at once; the answer and what Claude does arrive over the next seconds |
| `get_chat` | The conversation's lines after serial `after` (at most `limit`, 1 to 256, default 64), oldest first: `kind` is `you`, `claude`, `tool` (a tool Claude called: `tool` names it, `text` is its arguments), `result` (what came back, with `ok`), `note` or `error`. Also `busy` (Claude is working), `writing` (the words of Claude's answer as far as they have come, "" when none is on its way: they become a `claude` line once the answer is whole; to be given only the new words, pass the last reply's `writing_id` and its `writing_end` as `writing_from`, and `writing` starts at the reply's `writing_from`, which is 0 again for another answer), `after` (pass it to the next call), `latest` and `oldest` (2,000 lines are kept), `started` (false until the first message is sent) and, once started, `key_found`, `model`, `input_tokens` and `output_tokens` so far. `asking` is the command of Claude's the person is being asked about in the editor's window (`command`, `args` as text, `args_hidden`: bytes of it too long to show), or null |
| `stop_chat` | Stops Claude's work on the last message: no further commands run (one running now finishes). What it already did stays (undo takes it back). The work ends a moment later: `busy` says when |
| `clear_chat` | Forgets the conversation; the next message starts a new one |

Claude's answer shows in the Chat panel while it is being written. If you
stop it part way, or the connection breaks, what had come stays to be
read, marked with " …", and the note under it says that Claude will not
remember that unfinished answer.

Claude can look at the editor: when it runs `capture_screenshot`, the
picture goes to it with the command's result (up to four pictures a
command, PNG or JPEG, 3.5 MB each), and the Chat panel's line for that
result says "(with a picture)". A picture is a picture of your editor's
window as it is, panels included, and like your words it is sent to
Claude's service. The conversation keeps at most six pictures (8 MB, which
is also the most one command's result may bring): when another would go
over, the oldest are replaced by a note until at most three (and half the bytes)
are left, and Claude takes another if it needs to look again. Should
Claude's service refuse a message, every picture is taken out, so the
next message is not refused for the same picture. A picture costs tokens
like text does (about 800 for the default size).

Claude does not get the several hundred commands as a list. It has three
tools: `find_commands` (search them by words), `describe_command` (one
command's description and arguments) and `run_command`. It cannot close the
editor or talk to itself through the chat's own commands, and it is told to
ask before anything that cannot be undone (writing or deleting files,
loading another scene). With "Ask me before changes" on, the editor itself
holds each changing command until the person has answered; Claude is told
to take a no as their decision and not to try another way. One message
may take up to 40 steps, then it stops
and says so. The model is Claude Opus 5.5; if its safety checks decline a
request, Claude's service retries it on the model it recommends instead
(server-side fallback) before giving up.

## Commands so far

| Command | Changes things | What it does |
| --- | --- | --- |
| `get_engine_info` | no | Version, graphics backend and GPU, validation layer, frames, frame times over the last 240 frames (average, median, 99th percentile, worst, hitches: frames 1.5x the median and 2 ms over it, and `recent_ms`, the times oldest first, with `recorded`, the count ever; wall clock), `gpu`: the GPU's own time for the newest finished frame (`frame_ms`) and per pass (`passes`: `name` and `ms`, from GPU timestamps; passes run twice, such as culling, are added up; 0 ms on the null backend), window size. With `phases_since` (a `recorded` count), `frame_times.phases`: where the main thread's time went in the frames from then on (the last 240 at most): `typical`, each phase's median ms, and `typical_cpu_ms`, the main thread's CPU time; `slow`, each frame over `phases_over_ms` (default 25) with its `frame`, `ms`, `cpu_ms`, `window` (the window itself was handled in it: moved, sized, minimised or restored, its focus come or gone, or asked to be drawn again several times in one poll; Windows holds a window's messages while its title bar is held, so a long `events` phase with this set is the desktop's doing) and `phases` (those of 0.05 ms or more). ## Adding a command

1. Write it next to the feature, with a JSON Schema for its arguments
   (`minimum`, `maximum`, `enum` and `required` keep AI calls honest) and a
   description written for the AI: what it does and anything surprising.
2. If it changes state, record a `Change` with undo and redo. If it fails
   halfway, return `CommandResult::failure`; recorded changes roll back.
3. Mark read-only commands `read_only`; they may not record changes. View
   state (window size, camera, panel layout) is not undoable, the same as
   when a person changes it by hand.
4. Test it through `CommandRegistry::execute`, and add it to
   `tools/mcp_smoke.py` if it is part of a workflow the AI will use.
